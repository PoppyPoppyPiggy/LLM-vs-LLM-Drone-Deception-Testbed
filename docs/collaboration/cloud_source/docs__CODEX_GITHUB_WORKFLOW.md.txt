# Codex와 GitHub 연결 운영

## 먼저 확인할 현재 상황

이 workspace에는 `a6f8600`을 기반으로 한 코드만 있고, 사용자가 붙여 준 다른 WSL 작업의
`docs/HIERARCHICAL_LLM_HONEYDRONE_PROTOCOL.md`,
`docs/HIERARCHICAL_PILOT_REPORT_20260909.md`, 26-condition 결과는 존재하지 않는다. 따라서
두 작업을 이미 연결됐다고 간주하면 안 된다. **같은 GitHub 저장소에 양쪽 branch가 실제로
push된 뒤** Issue에서 비교·선별해야 한다.

양쪽 작업 위치에서 각각 아래 결과를 Issue에 붙인다.

```bash
git remote get-url origin
git branch --show-current
git rev-parse HEAD
git log -5 --oneline --decorate
git status --short
```

두 branch가 원격에 보이면 다음으로 공통 조상을 확인한다.

```bash
git fetch origin --prune
git merge-base origin/<public-branch> origin/<hierarchical-branch>
git diff --stat origin/<public-branch>...origin/<hierarchical-branch>
```

`git merge-base`가 실패하면 unrelated history다. 이 경우 `--allow-unrelated-histories`로
즉시 합치지 말고, Issue에 파일·실험 프로토콜·결과 provenance를 기록한 뒤 필요한 변경을
새 integration branch로 옮긴다.

## 권장 구조

별도의 봇 스크립트를 저장소에서 무한 실행하지 않는다. 일반적으로 사용하는 구조는
**GitHub Issue(업무 명세) → Codex task(코딩) → feature branch/PR(결과) → GitHub Actions
(검증) → 사람 또는 Codex review(피드백)**다. GitHub가 두 작업 세션 사이의 공용 상태가
되므로 로컬 Codex와 Codex cloud를 함께 써도 대화 기록을 직접 연결할 필요가 없다.

## 한 번만 설정할 것

1. Codex/ChatGPT 계정 설정에서 GitHub 연결을 승인하고 GitHub App이 이 저장소에 접근할
   수 있게 한다. 조직 저장소라면 조직 관리자의 승인도 필요할 수 있다.
2. Codex cloud에서 `PoppyPoppyPiggy/LLM-vs-LLM-Drone-Deception-Testbed`를 선택하는 환경을
   만든다. Setup command는 `python -m pip install -r requirements.txt`, 검증 command는
   `python -m unittest discover -s tests -v`로 둔다.
3. GitHub의 기본 브랜치 보호에서 PR과 `.github/workflows/ci.yml`의 성공을 merge 조건으로
   사용한다.
4. 비밀 값은 GitHub/Codex secret 기능에만 저장한다. Issue, prompt, commit, trace에 API key를
   넣지 않는다. 현재 Ollama 기반 unit test에는 OpenAI API key가 필요하지 않다.

연결 승인과 저장소 선택은 계정 권한이 필요한 외부 설정이므로 Git commit만으로 대신할
수 없다. 이 저장소는 연결 이후 Codex가 일관되게 일하도록 `AGENTS.md`, Issue Form, PR
template, CI를 제공한다.

## 두 Codex 작업을 실제로 연결하는 기준

다음 네 조건이 모두 충족되어야 “연결됐다”고 말할 수 있다.

1. 두 작업이 같은 GitHub repository URL을 가리킨다.
2. 양쪽 HEAD가 GitHub의 서로 다른 branch로 push되어 있다.
3. 하나의 reconciliation Issue에 두 branch 이름과 HEAD SHA가 기록되어 있다.
4. Codex cloud와 로컬 Codex가 그 Issue 및 연결된 PR URL을 입력으로 사용한다.

채팅에 커밋 해시나 “PR을 만들었다”는 문장만 붙이는 것은 연결이 아니다. GitHub에서 해당
branch, commit, PR URL을 실제로 조회할 수 있어야 한다.

### WSL 작업을 올린 뒤 사용할 reconciliation prompt

```text
Reconcile the two branches recorded in GitHub Issue #<number>. First verify each remote branch and
HEAD SHA. Read the hierarchical protocol/pilot files only from the branch where they actually exist.
Do not merge unrelated histories wholesale. Produce a file-level inventory of (a) shared code,
(b) v8-only evidence, (c) hierarchical-only protocol/results, and (d) conflicting claims. Create an
integration branch from the issue-designated canonical branch, port only reviewed changes, preserve
result provenance, run offline tests/audits, and open one linked PR. Never describe a local-only
commit or metadata-only PR record as present on GitHub.
```

## 이슈에서 Codex 작업 시작

1. GitHub에서 **Experiment / design change** Issue를 작성한다.
2. `Codex task prompt` 항목을 완성하고 실험 예산을 승인한다. 전체 LLM 실험을 승인하지
   않았다면 `smoke-only`로 둔다.
3. Codex cloud에서 해당 Issue URL을 새 task에 붙여 넣고 아래처럼 요청한다.

```text
Implement GitHub Issue #<number> in PoppyPoppyPiggy/LLM-vs-LLM-Drone-Deception-Testbed.
Read AGENTS.md and CONTRIBUTING.md first. Work on a feature branch and open a PR linked to the
issue. Add a focused FANET unit test before behavior changes, run the required checks, preserve
evaluation-only theta, and do not run a full LLM experiment unless the issue explicitly approves
the model/seed/episode budget.
```

Codex 연결 화면에서 Issue를 직접 선택하거나 할당하는 기능이 보이면 같은 Issue를 선택하면
된다. UI 명칭이 달라도 핵심은 **Issue URL/번호를 task 입력에 포함하고 결과를 동일 Issue에
연결된 PR로 반환하는 것**이다.

## PR에서 상호작용

CI가 실패하거나 설계 검토가 필요하면 PR comment에 구체적인 변경 요청을 남기고 같은 PR을
대상으로 Codex follow-up task를 실행한다.

```text
Continue PR #<number>. Read the newest review comments and CI failures. Address only unresolved
comments, rerun CONTRIBUTING.md checks, push to the existing PR branch, and summarize evidence
separately from interpretation.
```

자동 review 기능을 계정에서 활성화했다면 해당 기능을 사용하되, merge는 사람이 결과와
논문 주장을 확인한 뒤 수행한다. 코드가 통과했다는 사실과 연구 가설이 입증됐다는 결론은
같지 않다.

## 로컬 Codex와 함께 쓰기

cloud task가 만든 branch를 WSL에서 이어받을 수 있다.

```bash
gh auth login                         # 최초 한 번
git fetch origin
gh issue view <issue-number> --comments
gh pr checkout <pr-number>
codex
```

로컬 Codex에는 다음만 입력한다.

```text
Continue PR #<number>. Read AGENTS.md, CONTRIBUTING.md, the linked issue, review comments, and CI
status before editing. Keep working on this PR branch and push evidence-backed fixes only.
```

반대로 로컬에서 만든 branch/PR도 push한 뒤 Codex cloud task에 PR URL을 주면 이어서 검토할
수 있다. 두 Codex 인스턴스가 동시에 같은 branch를 수정하게 하지 말고, 한쪽이 push를
끝낸 후 다른 쪽이 `git pull --ff-only`로 인계받는다.

## 자동화 범위

자동화해도 좋은 것:

- Issue를 기준으로 branch와 PR 생성
- unit test, compile check, formatting/check 실행
- CI 실패와 review comment를 기반으로 제한된 수정
- 승인된 새 tag로 smoke run 실행

사람의 승인을 유지할 것:

- full 모델/seed/episode 비용
- 기존 논문 결과 교체
- 통계적 효과에 대한 최종 주장
- merge와 release
